## Context

当前设置页由 `lib/client.js` 的单一客户端入口渲染，已具备同一 `settings.section` 中的导入、连接配置和套件工作台，并使用局部 DSH 主题令牌、原生语义控件、`details/summary`、请求序号保护及现有确认对话框。详见 `proposal.md` 与 `specs/plugin-settings-ui/spec.md`。

本设计只调整 Client 的展示结构和局部展示状态：底层 RPC 方法、参数/结果、Registry 数据模型、Host 校验、请求执行和安全策略均保持不变。当前已存在的 Operation 编辑器、Service Target Endpoint 编辑器和删除/写策略确认层必须继续作为既有交互边界。

## Goals / Non-Goals

**Goals:**

- 用稳定、低留白的列表行替换 Operation 与 Service Target 的高卡片堆叠，同时让窄容器中的长文本可读且不溢出。
- 通过语义分组/折叠降低设置页首屏高度，并使默认展开状态服务于当前任务。
- 对数量较多的 Operation 和 Service Target 使用前端渐进展示，明确剩余数量，并提供键盘可用的显示全部/收起控制。
- 将 loading、empty、partial error、retry、dirty、delete confirmation、write-policy confirmation 等既有状态原样保留在新的布局容器中。
- 延续 DSH token、focus-visible、原生 button/summary 语义、现有容器查询和 Host-only 安全边界。

**Non-Goals:**

- 不改变任何 RPC 名称、调用参数、返回投影、请求流程或错误码映射。
- 不新增连接测试，不实现 Host/RPC/Registry/Typert/认证或安全策略逻辑。
- 不改造套件名称输入框高度，不进行完整中英文术语统一，不新增持久化的用户布局偏好。
- 不引入第三方 UI 框架、全局样式、独立路由或新的 DSH Slot。

## Decisions

### 1. 在现有 `Settings` 内维护轻量展示状态

新增两个列表的展开状态（例如 Operation 与 Service Target 各一个 boolean）以及设置分组的本地展开状态，状态只属于 `Settings` 组件生命周期。列表数据仍来自现有 refresh 结果；展开/收起只决定渲染切片，不过滤、删除或改写数据。

**原因：**满足渐进展示和刷新后保持用户选择，同时不引入新的 RPC 或持久化 schema。相比将状态写入 Registry，这种方式不会把纯视觉偏好误当成业务配置；相比拆成新 Slot，不会增加宿主契约风险。

**替代方案：**

- 持久化每个用户的折叠偏好：首阶段收益有限，却需要新的存储/同步语义，排除。
- 为每类列表新增远程分页：会改变请求契约和加载/错误语义，超出范围，排除。

### 2. 使用固定、可审查的初始展示阈值与切片

对当前范围内的 Operation 和 Service Target 分别使用小型固定初始阈值（建议 6 条，最终以实现常量集中定义）。数量超过阈值时渲染前 N 条，并在同一列表尾部显示“还有 X 个，显示全部”；展开后渲染完整列表并提供“收起”。数量不超过阈值时不渲染多余控制。

**原因：**简单、可预测、无需服务端分页，能直接解决卡片瀑布。控制文案同时携带剩余数量，避免用户误以为数据缺失。稳定 ID 继续作为 React key，列表刷新不会依赖 index。

**替代方案：**

- 无限滚动：会降低键盘和位置可预测性，也容易与设置页滚动容器冲突，排除。
- 搜索/筛选作为唯一方案：适合定位但不能满足用户快速浏览全部配置，且会扩大交互范围，排除。

### 3. 以行内网格 + 响应式折行为列表骨架

Operation 行保留 Method、名称/ID、Path、Target/状态和动作区；Service Target 行保留名称、环境/Endpoint/Operation 摘要、可用性状态和编辑/删除动作。桌面端使用 `minmax(0, 1fr)` 的内容列和不收缩的动作列；窄容器通过已有 container/media 断点改为可换行或动作区独占一行。行之间使用 hairline border 或 layer surface，不为每项添加重阴影。

**原因：**把用户扫描最需要的字段保留在一行，同时把现有按钮作为同一行的可聚焦控件，不破坏操作路径。`min-width: 0`、`overflow-wrap: anywhere` 和显式动作区可以防止长 ID、Path 或 Target 名称撑破嵌入式设置区域。

**替代方案：**

- 每项使用 `details` 隐藏元数据：能压缩高度，但会把基础识别信息藏起来，并增加逐项键盘操作成本，排除。
- CSS-only 隐藏字段：可能使重要状态只在视觉上消失，且难以保持辅助技术等价信息，排除。

### 4. 主要设置内容使用语义 `details/summary` 分组

把导入、连接配置和套件/Operation 工作台放入清晰的顶层分组；连接配置内部继续保留 Environment → Service Target 的顺序。默认仅展开最相关的工作区（已有套件时优先套件/Operation；没有套件时优先导入），其余分组可通过 `summary` 打开。若已有编辑器、错误、未保存草稿或正在进行的操作，则包含该状态的分组必须保持可见/展开，避免把恢复入口藏起来。

**原因：**项目已经使用 `details/summary` 作为 Operation 和 Endpoint 的渐进披露机制，复用原生语义可自然支持 Enter/Space、`aria-expanded`、焦点和无需自建弹层的键盘路径。将分组状态放在组件本地能避免刷新时强制回到默认状态。

**替代方案：**

- 自定义 tab：需要完整 tablist/箭头键/隐藏内容语义，并可能让跨区域比较变得困难，首阶段不采用。
- 纯 CSS 折叠：缺少可靠键盘和辅助技术状态，排除。

### 5. 保持状态处理与安全边界在布局层之下

列表行的操作回调继续调用现有启用/禁用、编辑、删除入口；编辑器、删除 dialog、写策略确认、错误提示和重试不重写。refresh 继续保留既有请求序号、mounted guard 和部分成功数据；展示切片不能把未加载、失败或未知计数转换成空列表/零。客户端不读取、拼接或展示超出安全视图的 Endpoint、Host/CIDR、凭据或 secret。

**原因：**这次变更是布局/信息密度优化，而不是数据或权限重构。将状态与安全逻辑保持在现有路径中，可以最大限度降低回归风险，并满足需求中“保留现有交互”和“不修改 API 请求和安全策略”的硬约束。

## Risks / Trade-offs

- [Risk] 固定阈值可能在某些设置容器高度下仍偏大或偏小 → 将阈值集中定义并在 320–375px、480–560px、680px 及桌面宽度下验证；后续可在不改变契约的情况下调整常量。
- [Risk] 折叠默认状态可能隐藏用户正在修复的错误或编辑器 → 错误、dirty 草稿、编辑状态和进行中的保存/删除操作拥有展开优先级；取消/关闭路径继续可见。
- [Risk] 紧凑行在窄屏上动作按钮换行后增加局部高度 → 采用容器查询、动作区整行布局和至少 40–44px 的可操作命中区，优先保证可用性而非强行单行。
- [Risk] 列表从卡片改为行后状态层级在暗色或自定义 skin 下不明显 → 继续消费 `--dsw-alias-bg-layer-*`、`--dsw-alias-border-*`、label/state/brand token，并提供兼容 fallback；不引入独立 palette。
- [Risk] 刷新期间的列表截断让用户误以为项目被删除 → 保留旧数据和 busy/加载状态，在展开控制附近明确使用当前已加载数量；失败时沿用现有错误和重试文案。
- [Risk] 改动单文件客户端时误触业务回调 → 先以局部渲染结构和 CSS 为主，保持现有回调引用；通过现有合同测试和手动状态矩阵验证，不修改 Host/RPC 文件。

## Migration Plan

1. 在 `lib/client.js` 中实现局部列表行、渐进展示状态和顶层分组，默认不改变 RPC 与业务 payload。
2. 运行现有测试/检查，确认打包清单与客户端合同未变；在真实 DSH Web 中刷新插件页面。
3. 验证加载、局部错误、空状态、显示全部/收起、编辑、启用/禁用、删除确认、未保存草稿和写策略确认路径。
4. 验证亮/暗主题、窄/宽容器、键盘操作、长文本和 reduced-motion；若布局回归，回滚本次 Client bundle 即可，不需要数据迁移或 Registry 回滚。
